Plan: unavailable media

What happens when a title we hold is deleted at the source. Today it silently rots; the aim is a first-class state the user can see, that stops the background retries, and that the Stremio addon handles without lying to the client.

1The state we're missing

"Unavailable" is reference-data health, not a user action and not a network condition. It belongs on the media row, next to the identity we already track there, and it is orthogonal to everything else. 

stateDiagram-v2
  [*] --> Available: hydrated from TMDB
  Available --> Unavailable: TMDB answers 404
  Unavailable --> Available: a later check finds it again
  Available --> [*]: never (we do not delete media rows)
  Unavailable --> [*]: never

  note right of Unavailable
    tracking, events and cached images
    are untouched - only refresh stops
  end note
  • A user's relationship with a title never changes because the catalogue did. Removing it from their list would be deleting their data to fix our reference data.
  • Self-healing by construction. Nothing here is terminal: the same monthly re-check that fills in a late IMDb id also clears this state if TMDB restores the entry.
  • It must be stored, not inferred. Right now the only signal is "the fetch failed", which is indistinguishable from being offline — which is exactly why the app shows the title as if the network were down.

2The change, by layer

One nullable column and a predicate in four places. The predicates are the interesting part: two of them currently make a deleted title un-stoppable.

LayerChangeWhy
schema media.unavailable_at (integer ms, nullable) the state itself; nullable means "available", so every existing row is correct with no backfill
refresh on a 404 set it, and ack instead of retrying a 404 is an answer, not a transient failure
sweep all four enqueueStaleMedia branches exclude it today an undated or future-dated movie is selected every night forever — 5 TMDB calls a night, per dead title
needsRefresh return false when unavailable it currently ignores refreshedAt for movies, so no timestamp tweak can stop it
alias job monthly re-check also clears or re-confirms the state one job owns "does TMDB still have this?", so nothing needs a second scheduler
sync MediaRecord.unavailableAt, version bump on change the client learns it through the existing version-diff channel — no new endpoint
client badge on the card and the detail page (§3) the user's actual ask
legacy data normalise release_date = '' to NULL (11 rows) '' fails IS NULL and reads as a past date, making those titles permanently unrefreshable for an unrelated reason

3The label

Muted and informational, never an error. The title stays in the list, keeps its poster and its progress; only the promise of freshness is withdrawn.

SurfaceTreatment
poster card Unavailable — small pill in the card's corner, same weight as other meta, no red
detail page one line under the title: "No longer listed on TMDB — details and artwork may be out of date."
affordances hide/disable "refresh"; keep everything the user can still do (track, rate, favourite, mark watched)
accessibility the pill carries text, not just a colour; the detail line is the aria description
offline orthogonal — a title can be unavailable and offline, or unavailable while online. Two different pills.
  • Not an error state. Nothing failed for the user; the source changed. Red or a blocking dialog would misdescribe it and train people to dismiss it.
  • The copy names the source. "No longer listed on TMDB" tells the user where the truth went, which is what makes a missing feature tolerable.

4Correcting the Stremio addon plan

The addon cannot express "unavailable", and the tempting shortcuts are all wrong. LibraryItem.removed and temp mean other things — setting removed: true makes Stremio delete the item, and temp: true marks a title that is not really in the library. Either would destroy user state to signal a metadata problem. 

flowchart LR
  A["title Marquee knows"] --> B{"has an IMDb alias?"}
  B -->|"no"| C["cannot be exported<br/>surface the count on /configure"]
  B -->|"yes"| D{"TMDB still has it?"}
  D -->|"yes"| E["export normally"]
  D -->|"no"| F["<b>still export</b><br/>name, poster, watch state<br/>IMDb still knows the title"]

  style F fill:#00201d,stroke:#2dd4bf,color:#e6e8ea
  style C fill:#1a1e22,stroke:#f0b429,color:#e6e8ea
  • Unavailable is a Marquee state only. Stremio keeps the title and keeps working — the watch state it carries is real, and the poster is a cached URL. The bridge changes nothing on the datastore for this.
  • The gap is the missing alias, not availability. A title with no tt… cannot be addressed by an IMDb-keyed client at all, so that — not a 404 — is what hides a title from Stremio. The /configure status page should say how many are in that state, because it is the only place a user could ever learn it.
  • Inbound needs a terminal state too. A tt… Stremio knows and TMDB does not resolve to anything, so today it would queue and retry forever. After N attempts it must become a visible "couldn't import" entry on /configure — never an infinite retry, and never a minted row.
  • Do not invent a LibraryItem field. Stremio silently ignores unknown fields, so a custom marker would look implemented while doing nothing.

5Decisions to settle

1 — Where does the label appear?

Recommendation: poster card pill and a line on the detail page. The card is where the user browses; the detail page is where the explanation lives.

2 — Does an unavailable title still get refreshed by anything?

Recommendation: no scheduled refresh; the monthly alias re-check is the only thing that touches it, and that is what clears the state if TMDB restores it.

3 — What does the addon do with an unavailable title it can already address?

Recommendation: keep exporting it unchanged. Stremio's copy keeps working and the user's watch state there stays valid.

4 — Inbound tt… that TMDB does not have at all?

Recommendation for v1: after N attempts, drop it and list it on /configure as "couldn't import". The durable fix is a custom media entry that keeps the user's watch state, which belongs to the linking epic — this plan should not pretend to solve it.

5 — The 11 legacy release_date = '' rows?

Recommendation: normalise to NULL in the same migration, and make movieUnreleased treat '' as "no date" so new bad data cannot reintroduce it.

Evidence: two deleted movies in production (both 404 at TMDB, both tracked by a user, both frozen rather than looping only because their release_date happens to be ''). 13 titles are in the buckets that would loop — 12 future-dated, 1 undated.
