Sync activity: add · watch · remove

Five flows through the same machinery: Stremio's addon surface inbound, a token-authenticated model API, and an event log that the bridge only ever nudges. Every branch below is a decision that already exists in code or is specified for the bridge.

1Add a movie in Stremio → it appears in the Marquee watchlist

The long path, including the one place a row is ever created. Note what the client does not do: it never posts an event. It states an intent and lets the server decide which events that means.

  • Why /find exists at all: Stremio speaks IMDb ids and Marquee speaks TMDB ones. The reverse lookup is the only place the two vocabularies meet, and it happens behind our API so the bridge never holds a TMDB key.
  • The reply is a lie Stremio accepts. {success:true} is ignored and the call is never retried, so the bridge cannot answer with the unresolved case. That's why the message stays queued instead.

2Marked watched in Stremio

Same inbound path, different intent. The only new information is videoId, and the rule is deliberately asymmetric: a movie is one unit, so "watched" needs no episode; a show is not, so we refuse to guess. 

flowchart TD
  A["user marks a title watched"] --> B["action=watched<br/>videoId=tt0898266:9:17 - or absent"]
  B --> C{"type?"}
  C -->|"movie"| D["no videoId is normal<br/>PATCH /api/v1/library/movie/tt…<br/>{ status: 'completed' }"]
  C -->|"show"| E{"videoId present?"}
  E -->|"yes"| F["bridge splits season / episode<br/>PATCH { episodes: [ {season:9, episode:17, watched:true} ] }"]
  E -->|"no"| G["mark nothing<br/>log it, surface as unmappable<br/>never infer "all episodes""]

  D --> H["translator compares against the projected state"]
  F --> H
  H --> I{"already watched?"}
  I -->|"yes"| J["nothing emitted"]
  I -->|"no"| K["one episode.watched event<br/>or one status_changed"]
  K --> L["projection: episode_watches / tracking"]
  L --> M["show status untouched by episode marks"]

  style G fill:#00201d,stroke:#2dd4bf,color:#2dd4bf
  style J fill:#00201d,stroke:#2dd4bf,color:#2dd4bf
  • Why a bare "watched" on a show marks nothing. An older series can run twenty seasons; reading one ambiguous signal as "every aired episode" would fabricate hundreds of watches, and a wrong bulk mark is tedious to unpick by hand.
  • "Mark all watched" still exists — it is simply never inferred. The app has an explicit bulk season/series action, and the API accepts an explicit episode list, so a client that really means everything can say so.
  • The withdrawn intent is visible, not silent. An unmappable watched lands on the bridge's status page, so "I marked it in Stremio and Marquee never noticed" is answerable.
  • Aired-only, by air date. Where a specific episode is named, an unaired episode is still never marked watched — watchability derives from air_date, not from a season count.

3Marked watched in Marquee → flows back to Stremio

The outbound direction has no local event it can carry: a merge needs Stremio's state, and only an API call gets that. So the trigger is a nudge, and the nudge is the per-handle alarm. 

flowchart TD
  subgraph C1["Marquee client"]
    A["user ticks an episode"] --> B["optimistic IndexedDB write<br/>+ queued episode.watched event"]
  end

  subgraph W1["apps/web"]
    B --> C["POST /api/sync (events only)"]
    C --> D["projection → episode_watches"]
    D --> E["sequence advances"]
  end

  subgraph B1["bridge"]
    E -.->|"nudge: no payload, just "this user changed""| F["DO alarm, coalesced ~30s<br/><i>fifty taps → one reconcile</i>"]
    F --> G["GET /api/v1/library?since=cursor"]
    G --> H["datastoreGet libraryItem"]
  end

  subgraph M1["3-way merge, per item"]
    H --> I{"changed since the snapshot?"}
    I -->|"neither side"| J["nothing to write"]
    I -->|"Marquee only"| K["watched bits UNION"]
    I -->|"both, different"| L["union wins for watched<br/>removed: not-removed wins<br/>status: the changed side"]
  end

  K --> M["datastorePut, changed items only<br/>state.watched bitfield, videoId,<br/>timesWatched, lastWatched"]
  L --> M
  M --> N["snapshot = merged"]
  N --> O["re-arm: daily floor,<br/>backoff on failure"]

  style K fill:#00201d,stroke:#2dd4bf,color:#2dd4bf
  style L fill:#00201d,stroke:#2dd4bf,color:#2dd4bf
  • Union, not last-write-wins. Stremio knowing episode 5 and Marquee knowing episode 6 resolves to both. Choosing a winner would delete a watch that happened.
  • No clock arbitrates. _mtime is a device clock bumped by playback progress, so it is recorded and never used to decide a conflict.

4Removed in Stremio

flowchart TD
  A["user removes the title in Stremio"] --> B["action=libraryRemove"]
  B --> C["enqueue → DO → PATCH { removed: true }"]
  C --> D["translator: only if not already removed"]
  D --> E["one `removed` event"]
  E --> F["projection: tracking.removed = true<br/><b>a tombstone, not a delete</b>"]
  F --> G["DO records the last-applied marker<br/>so the outbound pass does not re-add it"]
  G --> H["every device sees the tombstone;<br/>the user can restore it and its progress is intact"]

  style F fill:#00201d,stroke:#2dd4bf,color:#2dd4bf
  • Removal is a state, not a deletion. Episodes watched, the rating and the original add date all survive, so "oops, put it back" is a status change rather than a re-add.
  • Echo suppression is what makes this safe. Without the marker, the next reconcile would see "Marquee says not-removed" and write the title straight back.

5Removed in Marquee → Stremio follows

flowchart TD
  A["user removes the title in Marquee"] --> B["removed event → projection"]
  B --> C["DO alarm → reconcile"]
  C --> D["GET /api/v1/library?since=cursor"]
  D --> E["datastoreGet"]
  E --> F["diff against the snapshot"]
  F --> G["datastorePut: removed = true on that LibraryItem"]
  G --> H["<b>not</b> a delete - the item and its<br/>watch history stay in Stremio's datastore"]
  H --> I["snapshot marks it removed"]
  I --> J["if the user re-adds it in Stremio,<br/>'not removed wins' and the title comes back"]

  style G fill:#00201d,stroke:#2dd4bf,color:#2dd4bf
  • removed: true, never a datastore delete. Deleting the item would discard the watch state that makes a restore possible, and it is the same trap as using removed to signal an unavailable title.
  • Conflicts preserve data. If both sides changed in the same window, the merge prefers "not removed" — a wrong re-add is recoverable, a lost watch history is not.
Same-origin notes: the addon surface is public by necessity (Stremio's servers call it and cannot authenticate), which is why the handle is treated as a bearer capability and revoking it is the kill switch. Everything else — tokens, merges, the event log — stays behind /api/v1. The exact extra encoding in the addon URL (query string vs path segment) is the one detail still to be confirmed by the spike against a real Stremio account; the bridge accepts both until then.
