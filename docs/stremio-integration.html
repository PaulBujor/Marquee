Stremio ↔ Marquee

Two-way library and watch-state sync, without Marquee learning what Stremio is. Eight diagrams: where the pieces run, what identity means, how each direction flows, and the rule that decides conflicts.

1Two deployments, one HTTP contract

The bridge is a separate Worker with its own deploy and its own bindings. It holds no database: everything durable about a user lives in their Stremio account, in the per-handle Durable Object, or in D1. One owner per fact, so no two copies can disagree. The only contract between the two deployables is HTTPS under /api/v1.

2Identity: ours, theirs, and the aliases between

Every title has our own UUID. A provider-sourced title's UUID is derived from (provider, external_id), so any device derives the same id offline with no coordination. Stremio is IMDb-keyed and Marquee is TMDB-keyed, so the translation lives in media_external_ids — a table of aliases, never a column on the title.

  • PRIMARY KEY (media_id, provider) + UNIQUE (provider, external_id) — an external id names exactly one title, and a title has at most one id per catalogue.
  • A miss is a miss. resolveMediaId() returns null rather than falling back to the derived id: a derived id names a title nobody has stored, and treating it as real would report success for something never hydrated.
  • Watchability is derived from air dates, not a season-count field — one source for both "is this out yet" and the upcoming calendar.

3Inbound: the user acts in Stremio

Stremio calls the addon, we answer immediately, and the real work is enqueued — not waitUntil, which caps at 30s and never retries. The queue feeds the Durable Object, which serialises without needing a distributed lock. 

sequenceDiagram
  autonumber
  participant S as Stremio
  participant B as bridge addon
  participant Q as Queue
  participant D as DO per handle
  participant W as apps/web

  S->>B: GET /{handle}/library/movie/tt0133093/action=watched.json
  B-->>S: 200 success
  Note over S: the reply is ignored and never retried,<br/>so the bridge cannot rely on a second chance
  B->>Q: enqueue inbound command
  Q->>D: deliver, at least once
  D->>D: take lock, resolve handle
  D->>W: PATCH /api/v1/library/movie/tt0133093
  W->>W: verify token, resolve id via alias
  W->>W: translate intent to events, then project
  W-->>D: current state
  D->>D: record last-applied marker
  D-->>Q: ack
  • Deliveries are at-least-once, so every inbound command must be idempotent — replaying "watched" twice must equal "watched" once.
  • The last-applied marker is what stops the outbound reconcile from echoing this change straight back to Stremio as if Marquee had made it.

4Outbound: the user acts in Marquee

A cron walks every handle. The Durable Object reads both sides, merges against its snapshot, and writes only what actually changed — in both directions, because a reconcile is not a one-way push. 

sequenceDiagram
  autonumber
  participant C as cron
  participant D as DO per handle
  participant W as apps/web
  participant X as api.strem.io

  C->>D: reconcile(handle)
  D->>D: take lock
  D->>W: GET /api/v1/library?since=cursor
  W-->>D: Marquee state
  D->>X: datastoreGet libraryItem
  X-->>D: Stremio state
  D->>D: 3-way merge against snapshot
  alt something changed
    D->>X: datastorePut, changed items only
    D->>W: PATCH, only what Marquee is missing
    D->>D: snapshot = merged
  else nothing changed
    D->>D: no write, no echo
  end
  D->>D: release lock
  • The state diff is the source of truth; an event is only a trigger. The merge, not whichever side ran last, decides the outcome.
  • Stremio's write API is unofficial — that is why the account client is one isolated module behind a spike that pins the real payloads.

5The merge: why nothing is ever lost

Per item there are three inputs: the snapshot (what both sides last agreed on), Marquee now, and Stremio now. The snapshot is a per-episode watched set — not a hash — because a hash can only say "they differ", and then something has to win. 

flowchart TD
  A["one item, present on both sides"] --> B{"in the snapshot?"}
  B -->|"new on one side"| C["adopt it, no conflict"]
  B -->|"known"| D{"changed since the snapshot?"}
  D -->|"neither side"| E["nothing to do"]
  D -->|"one side"| F["apply that side"]
  D -->|"both sides"| G{"same field?"}
  G -->|"yes"| H["they agree"]
  G -->|"no"| I["watched bits: UNION<br/>removed: not-removed wins<br/>status: follow the changed side"]
  I --> J["no watched bit is ever deleted"]

  style A fill:#1a1e22,stroke:#2dd4bf,color:#e6e8ea
  style I fill:#1a1e22,stroke:#f0b429,color:#e6e8ea
  style J fill:#00201d,stroke:#2dd4bf,color:#2dd4bf
  • Union, not last-write-wins: Stremio knowing episode 5 and Marquee knowing episode 6 resolves to both. Choosing a winner would delete a watch that happened.
  • _mtime is recorded, never arbitrating. Stremio bumps it on playback progress, so it carries device time, not intent order — using it to resolve conflicts would prefer whichever device was playing most recently.
  • Scope is movies and series. channel and tv library items are ignored: never imported, and never mistaken for deletions.

6An id we have never seen

Stremio is IMDb-keyed and we are TMDB-keyed, so the first time a title arrives from Stremio it has to be translated, not seeded. There is exactly one row-creating call in this flow, and its parameter type is what stops the other one from ever existing. 

flowchart TD
  A["Stremio: tt0133093"] --> B{"alias for (imdb, tt0133093)?"}
  B -->|"hit"| C["that media_id"]
  B -->|"miss"| D["TMDB /find/tt0133093<br/>external_source=imdb_id"]
  D --> E{"what came back?"}
  E -->|"one result, type matches"| F{"alias for (tmdb, movie/603)?"}
  E -->|"nothing"| G["422 unresolved<br/>retry later, never mint"]
  E -->|"ambiguous, or type mismatch"| H["422 unresolved<br/>never guess"]
  F -->|"hit"| C
  F -->|"miss"| I["seedMediaId(tmdb, movie/603)<br/>the only row-creating seed"]
  I --> J["hydrate, then write BOTH aliases"]
  J --> C
  C --> K["done"]

  style I fill:#00201d,stroke:#2dd4bf,color:#2dd4bf
  style G fill:#1a1e22,stroke:#f0b429,color:#e6e8ea
  style H fill:#1a1e22,stroke:#f0b429,color:#e6e8ea
  • seedMediaId takes HydratableProvider, which is ['tmdb'] — so seedMediaId('imdb', …) is a type error, not a convention. An IMDb id can only ever be an alias.
  • Because the seed derives from the TMDB id, a bridge import and an in-app add that race each other compute the same UUID and collapse into one row. Deriving from the IMDb id would give two — which is the entire bug this avoids.
  • /find is the reverse mapping: an IMDb id in, a TMDB id out. It is the only place the two catalogues meet, and it lives behind our API so the bridge never holds a TMDB key.

7What actually triggers a reconcile

Outbound work has no local event it can carry: a merge needs Stremio's state, and only an API call gets that. So the trigger is not a payload, it is a nudge. The nudge is a Durable Object alarm rather than a Queue, because the DO already owns the lock and the snapshot — and a Queue cannot express per-user partitioning at all. 

flowchart LR
  M["a change in Marquee<br/>or a manual sync now"] --> AL
  Q["inbound command<br/>Queue — the only durable edge"] --> A
  DF["daily floor"] --> A

  subgraph DOH["Durable Object per handle"]
    AL["setAlarm(now + 30s)<br/>coalesces a burst into one"]
    A["alarm() then reconcile"]
    B["re-arm: backoff on failure,<br/>daily floor otherwise"]
    AL --> A
    A --> B
    B --> AL
  end

  N["a Queue cannot be the partition:<br/>no per-key ordering, and max_concurrency<br/>is queue-wide, not per user"]

  style N fill:#1a1e22,stroke:#f0b429,color:#e6e8ea
  style DOH fill:#00201d,stroke:#2dd4bf,color:#e6e8ea
  • Queue — inbound only, where the event is born outside the DO and has to survive being dropped on the way in.
  • Alarm — one per handle. Debounce, coalescing and retry-with-backoff come with the primitive; there is no extra binding, no DLQ and nothing to shard.
  • Daily floor — so a dead alarm means a handle is stale and visible on its status page, not stuck forever.
  • The sweeper that would fix a dead alarm is deliberately skipped: enumerating every handle runs into the 50-subrequest-per-invocation limit, and the bridge keeps no database to page through.
