Identity discrepancies: TMDB ↔ IMDb

Where the two catalogues disagree, which of those disagreements break the sync, and what each one should do. Written before the bridge, because every one of these becomes a silent duplicated or unresolvable title at the client.

1The three mappings, not one

Most of the difficulty disappears once you stop treating "the identity" as one edge. There are three, they fail differently, and only one of them reads our own id back. 

flowchart TB
  TT["IMDb<br/>tt0133093"]
  TM["TMDB<br/>movie/603"]
  AL[("media_external_ids<br/>PK(media_id, provider)<br/>UNIQUE(provider, external_id)")]
  M["media row<br/>id = uuid5('tmdb:movie/603')"]

  TT -->|"inbound: resolve"| AL
  TM -->|"inbound: resolve"| AL
  AL --> M
  TM -->|"seed on first create"| M
  M -->|"outbound: needs a tt"| AL
  • Inbound — a client states tt…; we must land on the stored title. Alias hit, or reverse lookup, or refuse.
  • Outbound — we must emit a tt… for a title. If no alias exists, there is nothing to emit, and the title is invisible to the client.
  • Seed — the only row-creating path, and it is typed so only TMDB can mint a UUID. seedMediaId('imdb', …) does not compile.

2What asking TMDB can answer

Only four outcomes, and they are not interchangeable. Today all four collapse into "stamped" or "retry", which is what lost the no-IMDb-id-yet case. 

flowchart TD
  Q["ask TMDB about a title"] --> R{"response"}
  R -->|"200, imdb_id present"| OK["write the alias<br/><b>terminal</b>: never asked again"]
  R -->|"200, imdb_id null"| NONE["no id <i>yet</i><br/>re-check monthly"]
  R -->|"404"| GONE["entry deleted or re-namespaced<br/>settle, re-check monthly, surface"]
  R -->|"429 / 5xx"| RETRY["retry with backoff<br/>give up at 5 attempts"]

  style OK fill:#00201d,stroke:#2dd4bf,color:#2dd4bf
  style NONE fill:#1a1e22,stroke:#f0b429,color:#e6e8ea
  style GONE fill:#1a1e22,stroke:#f0b429,color:#e6e8ea
  • "No id yet" is not terminal. Every upcoming release lives here. IMDb assigns an id when a release is scheduled, so a title that has none in March usually has one by June. Stamping it once and never asking again makes it permanently unresolvable by tt….
  • A 404 is an answer, not a failure. It means the entry is gone. Retrying it five times a night forever is noise, not resilience — but re-checking it monthly is nearly free and self-heals when TMDB restores or re-lists it.

3The discrepancy classes

Grouped by which edge they break. handled = implemented now, partial = implemented but silent or lossy, silent = fails without trace, deferred = needs the linking model.

# Class Symptom Handling State
D1 TMDB has no IMDb id (imdb_id: null) outbound: nothing to emit; the title is invisible to the client not terminal — re-check monthly until an id appears was terminal
D2 TMDB entry deleted (404) cannot hydrate; nightly retries forever settle + re-check monthly; log loudly was retried
D3 Re-namespaced movie ↔ tv 404 in one namespace, the entry lives in the other typed conflict, then link old row to new identity deferred
D4 IMDb id with no TMDB match inbound: nothing to resolve to 422 unresolved; never mint a row from the tt id handled
D5 IMDb id matching several TMDB rows ambiguous reverse lookup pick by declared type; otherwise 422, never a guess handled
D6 Two TMDB titles claim one IMDb id UNIQUE(provider, external_id) rejects the second write keep the first, log the loser, surface as a duplicate candidate silent
D7 TMDB corrects an IMDb id PK(media_id, provider) cannot hold both alias must be replaceable; history belongs in the event log impossible
D8 Our UUID derives from a provider id that dies the row can never be refreshed, but user events point at it link old → new; never delete the row or its events deferred
D9 Format variance (TT…, bare digits, whitespace) resolve misses on a technically-correct id normalize before resolving; reject what is not tt\d+ partial
D10 Client declares the wrong kind (movie vs show) lookup in the wrong namespace misses report a typed conflict, not a generic unresolved — the fix is the client's partial
D11 Metadata drift (renamed, re-dated) stale display existing version bump on refresh handled

4The three that need a decision

Everything marked handled is a query or a branch. These three are not — they change what the alias table is, and they are much cheaper to settle now than after the bridge writes thousands of items through them. 

flowchart LR
  D6["<b>D6</b> silent duplicate<br/>two titles, one tt"] --> A1["log the loser<br/>+ surface a merge candidate"]
  D7["<b>D7</b> corrected id<br/>PK blocks the new value"] --> A2["alias = current answer<br/>(replaceable)<br/>history lives in events"]
  D3["<b>D3 / D8</b> re-namespaced<br/>or dead identity"] --> A3["<b>media.linked</b><br/>re-point, never delete"]

  style A3 fill:#00201d,stroke:#2dd4bf,color:#e6e8ea
  • D6 — the unique index is doing its job; the problem is it says nothing. Logging the rejected pair turns a lost title into a merge candidate someone can act on.
  • D7 — "append-only" is the right rule for the event log, and the wrong rule for a table whose job is to answer "what is this title's id now". The table should be replaceable; the media.linked event keeps the history.
  • D3 / D8 — this is what the linking epic exists for, and "Lando" is the first real specimen: a movie entry a user tracks whose TMDB id was deleted when the project became a series (tv/332982).

5The rule that covers all of them

One sentence, and every class above is an instance of it: an id that cannot be answered must never become a row. A missing mapping stays missing and gets re-asked; it never gets a guess, and it never gets a second row for the same title.

  • The two rows that motivated this audit, verified in production: movie/1178539 "Lando" and movie/1728565 "Sherlock Holmes 3" — both 404, both tracked by a real user, both unreleased projects that TMDB pruned.
  • Nothing here is specific to Stremio. D1–D11 are properties of using two catalogues; the bridge is just the first client that makes them observable.
Measured 2026-11-26: 695 TMDB-backed titles, 693 queried, 691 aliased, 2 stamped with no alias (both 404s) — the population D1/D2 would have frozen.
